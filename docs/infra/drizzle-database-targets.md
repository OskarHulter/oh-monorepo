# Drizzle database targets per workload

> Living reference. ADR 0009 ratifies Drizzle as the SQL framework; this doc carries the **per-workload DB picks** as they are decided.
>
> Tracked by `oh-monorepo-4dn`. Each workload's pick is decided when the workload is implementation-ready, not now. Mark a row as `committed` only when its follow-up ticket is closed.

`committed` means a follow-up ticket has closed with the migration in `packages/server/db/migrations/`. Until then the lean is a starting point, not a decision.

## Selection criteria (apply per workload)

When a workload becomes implementation-ready, walk the criteria in order. The first row that diverges between candidates is the deciding factor.

1. **Write volume + concurrency.** D1 has row-write limits (~1000 writes/s/database) and per-DB transaction scoping. If a workload pushes that ceiling, Postgres.
2. **Transaction shape.** If the workload needs cross-row transactions or row-level locking, Postgres. D1 transactions are scoped to a single request.
3. **Schema complexity.** JSONB, full-text search, custom types, pg-extensions → Postgres. SQLite can do JSON but the ergonomics are weaker.
4. **Replication / latency.** Edge-replicated reads needed everywhere → D1 or Turso. Single-region writes fine → Neon + Hyperdrive.
5. **Cost shape.** D1 bills per-row + per-storage; Neon bills per-compute + storage; Turso bills per-replica. Pick the curve that matches the workload's read/write ratio.
6. **Operational ergonomics.** D1 ships in the Workers binding model — no connection setup. Neon needs Hyperdrive + a connection string in env. Turso needs a token + libSQL client.

## Database options at a glance

- **D1.** SQLite at CF, native binding, simple migrations via Wrangler. Ceiling: write rate, transaction scope.
- **Neon + Hyperdrive.** Serverless Postgres + CF connection pooler. Full Postgres surface (JSONB, extensions, full-text). Cost: connection + compute.
- **Turso.** SQLite at edge with replication. Alternative to D1 when read-replication matters more than CF-native binding.
- **DuckDB.** **Not a Drizzle target.** Analytics layer only — see `oh-monorepo-b4b`.

## Repo layout (once a workload lands)

```
packages/server/
  db/
    schema.ts              # single source of truth
    migrations/            # generated by `drizzle-kit generate`, checked in
    client.ts              # dialect-specific Drizzle client
```

Workflow:

1. Edit `schema.ts`.
2. `drizzle-kit generate` produces a migration.
3. Typecheck flags every consumer that needs to update — fix at the call site, not in a runtime mapper.
4. Apply on deploy: `wrangler d1 migrations apply` (D1) or migration runner of choice (Postgres).

## Open questions (resolve at adoption time, not now)

- D1 row-size + transaction limits for our actual writes — measure before committing user-accounts / audit-log workloads.
- Hyperdrive setup cost: Neon connection + CF binding. Confirm at the first Postgres-targeted workload.
- Turso vs D1: replication latency tradeoff vs CF-native binding ergonomics. Decide if a workload genuinely needs cross-region read replicas.
